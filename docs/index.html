Context

Why this role exists now

75+retail banners, in nearly a dozen countries

Simbe sells Store Intelligence: Tally robots, Tally Spot fixed sensors and RFID scan the shelves, and the platform turns those scans into out-of-stock, pricing and planogram tasks for store teams and data for brands. The product has been proven. The challenge now is installing it fast enough. Moving from a contracted unit to a working robot in a store means a site visit, a network, a map and a validation period, and every one of those steps takes time.

The job posting confirms this. It merges physical deployment support and digital onboarding into one role so that one person owns each site from start to finish. Simbe plans to hire about two people on contracts through February 2027 to cover near-term rollout volume. It also asks for people who will automate the work rather than just do it.

My read: Simbe is paying for deployment throughput with consistent quality. Every deployment I own should go faster than the last, and every problem I hit should be less likely at the next site.

The job, as a sequence

One store, from contract to handoff

01Pre-deployment

What I'd do
Confirm every site requirement before anyone travels: Wi-Fi SSID and auth method, firewall egress approved by store IT, a dock location with power, traversal areas defined, and the robot serial and hardware checked as ready.
Where it breaks
Store IT hasn't allowlisted the robot. The SSID uses a captive portal or 802.1X that nobody mentioned. The planned dock spot has no outlet. The answers sit in an email thread instead of the site record.
What I'd automate
A preflight check that reads the site record and lists blockers by name, run at T-7 and T-2 days. Anything missing becomes a Jira subtask with an owner.

02Physical install

What I'd do
Guide a remote contractor through unboxing, dock placement, power-on and first checks in Front or Zendesk chat, with a voice call ready. Keep them on the procedure and record any deviations.
Where it breaks
Contractors vary in skill. Steps get skipped under time pressure. Photos and confirmations get lost in chat. Store hours limit when work can happen.
What I'd automate
Install checklist macros in the chat tool that ask for a photo at each checkpoint. Contractor replies get filed into the deployment ticket automatically.

03Network

What I'd do
Get the robot associated, addressed and talking to Simbe's backend, and confirm it can upload at full size. Check roaming across access points along the aisles, not only at the dock.
Where it breaks
DHCP exhaustion, blocked outbound ports, DNS filtering, weak signal deep in the aisles or near freezers, or VPN tunnels that drop when the robot changes AP.
What I'd automate
A scripted connectivity probe (DNS, TLS to each endpoint, measured upload throughput) that produces a one-page pass/fail report I can send to store IT as-is.

04Digital config

What I'd do
Build or review the store map, define traversal patterns and routes, and set scan schedules around store hours and busy periods.
Where it breaks
The store layout has changed since the survey. Seasonal displays block aisles. Schedules collide with restocking or cleaning. Config gets copied from a different store format.
What I'd automate
A config validator that diffs a site's config against a known-good template for that store format and flags anything unusual before go-live.

05Validation

What I'd do
Run the first scans and score them against Simbe's quality thresholds. If a metric falls short, find out whether the cause is the robot, the network, the map or the store.
Where it breaks
One bad aisle drags down coverage. Slow uploads are mistaken for a scanning failure. Teams disagree about which number counts as "good enough".
What I'd automate
A daily early-life health report per site for the first two weeks, with each metric trended against its threshold and a cause suggested for each miss.

06Handoff

What I'd do
Hand a healthy site to operations with a complete record: config, deviations, open issues and site contacts. Add anything new I learned to the playbook.
Where it breaks
Site knowledge stays in one person's head. The same failure repeats at the next site because nothing changed.
What I'd automate
Generate the handoff page in Confluence from the ticket history. Tag every issue with a root-cause category so patterns show up across sites.

Troubleshooting

Work bottom-up, write it down, escalate cleanly

The posting asks me to "triage root causes systematically and elevate with clear documentation." In practice I'd check the cheapest layer to rule out first, and I'd write each escalation so the engineer receiving it doesn't need to come back with questions.

Network

Is it reachable?

  • Link, IP, gateway, DNS
  • Egress to each required endpoint
  • Signal and roaming along the route
  • VPN tunnel state and MTU
Hardware

Is it physically healthy?

  • Docking contact and charge cycles
  • Camera and sensor status, lens condition
  • Drive, bumpers, e-stop
  • Anything that changed since the last good run
Software

Is it configured and running?

  • Service and node health, recent logs (Linux, likely ROS)
  • Config version vs template
  • Map and route validity
  • Schedule, timezone, store hours

Every escalation includes the symptom, the site and robot, what I ruled out and how, the logs or captures, and the impact on the deployment date.

Automation and tooling

What I'd build in the first 60 days

These follow the posting's own list (checklists, status tracking, config validation, reporting), ordered by how much manual work each removes per site.

Site preflight checker

Reads the site record and lists every unmet requirement by name. Runs on a schedule before install day.

Blockers found a week out cost an email. Found on install day, they cost a rescheduled contractor.

Network probe + report

One command on site that tests DNS, TLS to each endpoint, and upload throughput, and outputs a report I can share with store IT.

Turns "the robot can't connect" into a specific request IT can act on.

Config validator

Diffs each site's config against the template for its store format and flags the differences.

Catches copy-paste config mistakes before they turn into a bad first week.

Deployment status board

Jira automation plus a daily summary showing every assigned site, its stage, its blockers and its date risk.

Lets me run several deployments at once without losing track, and gives managers status without asking.

Early-life health report

Daily per-site trend of the five quality metrics against thresholds for the first two weeks.

Handoff becomes a decision based on data rather than judgment.

Failure pattern log

Every issue tagged by root cause, rolled up across sites, with the top patterns turned into new preflight checks.

This is the "detection or prevention mechanisms" part of the posting. It keeps the same problem from recurring at site 40.

Here's the kind of first version I mean, before I know Simbe's actual data model. It's small and readable, and it's useful from the first day.

# preflight.py — list what's still blocking a site before install day
REQUIRED = ["ssid", "wifi_auth", "egress_approved",
            "dock_location", "dock_power", "traversal_areas", "robot_serial"]

def preflight(site: dict) -> list[str]:
    blockers = [f"missing: {k}" for k in REQUIRED if not site.get(k)]
    if site.get("wifi_auth") in ("captive_portal", "802.1x"):
        blockers.append("wifi auth needs store IT action (MAC allowlist / cert)")
    if site.get("layout_survey_age_days", 0) > 90:
        blockers.append("layout survey is stale; confirm aisles before mapping")
    return blockers

My working method is the same one I wrote up in the Hermes project and use at Atlassian with Rovo agents. I decide what the tool should do and what "correct" means, the AI writes and audits the code, and I verify the results against real data before anyone relies on them. That's how I'd meet the posting's expectation that AI tools are "a core part of how you work."

What a Tuesday might look like

This is a hypothetical day with three sites at different stages, based on the posting's "multiple concurrent deployments."

07:30

Read the overnight preflight and health reports. Site C's upload speed dropped after 2 a.m., so I open a ticket before the store asks.

08:30

Site A install day. The contractor is on site. I go through the checklist in chat with photo checkpoints. The dock outlet is on a switched circuit, so we move the dock to the backup location already in the site record.

10:15

Site A network. The probe shows one endpoint blocked. I send the report to store IT, and the allowlist is updated within the hour.

12:00

Site B digital config. The validator flags a schedule overlapping the store's morning restock. I fix it and note the pattern for that banner.

14:00

Site A first mapping run and route setup. I watch coverage live, and a seasonal display blocks aisle 14.

15:30

Site C root cause: the store's ISP shaping traffic at night. I document it, escalate with evidence, and add a check to the probe.

16:30

Update Jira and the status board, and add the switched-outlet issue to the playbook's dock checklist.
